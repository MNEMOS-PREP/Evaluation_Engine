WHAT THIS MODULE NEEDS (upstream)
-------------------------------------------------------------------------------
Nothing here is required to START, and nothing is marked `required: true`.

For most modules that is a convenience. For M13 it is a rule: this is the
module that turns an answer into a number a student is told to trust, and a
score cannot depend on whether somebody else's service happened to be up.
Marking a dependency required would turn another team's outage into a student
losing their evaluation.

**a missing input narrows the scope of what we show, never the quality.** We
say "not measured", never zero, and never a fabricated stand-in.


WHAT THIS MODULE FEEDS (downstream)
-------------------------------------------------------------------------------
These consume M13. They are NOT dependencies — M13 never blocks on them — but
`TurnEvaluation` and the observation shape are contracts four modules read.

  MODULE  WHAT THEY TAKE FROM US
  ------  ----------------------------------------------------------------
  M04     one observation per (turn, concept), from the concept-bearing
          dimension, each carrying resolvable evidence
  M02     the coverage-ledger transition to 'scored'
  M16     version-scoped comparable scores, for longitudinal diagnosis
  M17     content scores and key-point coverage, for the fused timeline
  M19     dimension_score ledger entries with their evidence spans

Contract: `TurnEvaluation` is the stable surface. Additive changes are safe;
removing or renaming a field is a breaking change for five modules.

**The concept-bearing rule is the contract most easily broken by accident.**
Exactly one rubric dimension is `concept_bearing`, and its score is the one
that becomes mastery. Communication dimensions map only to communication
concepts. Get this wrong and communication quality silently becomes part of
technical mastery — a value nobody chose, inside θ, where nobody can untangle
it later. The rubric loader refuses to load a rubric that declares zero or two
(FR-13.22), which is why it is a load-time failure and not a code review.


SHARED PLATFORM CODE  —  a versioned dependency, not a copy
-------------------------------------------------------------------------------
    https://github.com/MNEMOS-PREP/Platform_Core   (public)   pinned at v0.6.0

  Backend    ai-core @ git+https://github.com/MNEMOS-PREP/Platform_Core@v0.6.0#subdirectory=python

**`EvidenceSpan` and `EvidenceRef` are platform contracts, not module code.**
M13 *produces* evidence; it does not get to decide what evidence is. The type
that carries "every number traces to evidence" lives in `ai_core.evidence`
because nineteen copies would drift, and that sentence would quietly stop
being true in whichever repo fell behind — while that repo's own tests kept
passing.

`ai_core.evidence.resolve()` is also what this module's own output is checked
against in the test suite. Using the platform's resolver rather than our own
is what makes AC-13.16 a gate instead of a self-assessment.

**Pinned by tag on purpose.** Tracking `main` is how you get a surprise
breakage on a Tuesday. Upgrading is deliberate: bump the tag, run the tests,
commit the bump.

RUNNING WITHOUT ANY OTHER MODULE
-------------------------------------------------------------------------------
    start_eval.bat                 API :8113
    cd Backend && .venv\Scripts\python -m pytest

Everything works. `GET /v1/deps` reports all three upstreams as absent and
names what each one would have added — which is the point: you can see the
degraded path without arranging for anything to be down.

    start_all.bat                  the same, plus every sibling module repo

`start_all.bat` reads the `depends_on` list in `module.json`, looks for each
repo checked out beside this one (`..\Memory`, `..\Question_Intelligence`),
and launches the ones it finds into the SAME terminal window. A sibling that
is not on disk is skipped silently, because that is the normal case and not
an error.
